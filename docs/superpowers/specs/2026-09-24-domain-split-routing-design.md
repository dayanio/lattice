# 国内直连分流设计：静态国内 IP 排除路由 + DNS 驱动的动态排除路由

**日期**：2026-09-24
**状态**：修订中（2026-09-25：分期改为「M1 单独可交付」，M2 在两条路线间待 M0/M1 数据决定，新增 §4.5 DNS 分域名备选），待书面评审

## 一、背景与动机

出口模式开启后，`0.0.0.0/1` + `128.0.0.0/1` 两条全局路由把设备**所有 IPv4 流量**收进隧道并从出口节点（香港）转出。实测：国内 App（抖音、微信、淘宝等）也走香港，带来三个问题：

1. 绕路变慢，且 CDN 解析被 `8.8.8.8`（经香港）影响，可能拿到境外节点；
2. 国内服务看到境外 IP，可能触发风控或限制；
3. 消耗出口机器的流量额度。

**期望：** 国内的域名/IP 直连，国外走隧道。

## 二、目标 / 非目标 / 成功标准

**目标**

1. 出口模式下提供"国内直连"开关：国内 IP 与国内域名的流量不进隧道。
2. 国外流量行为与现在完全一致（仍进隧道、经出口 NAT）。
3. Mac 与 iOS 行为一致，逻辑只在引擎里实现一次。
4. 隧道扩展的内存、唤醒次数、稳定性不劣于现在。

**非目标（本期不做）**

- 按域名规则的**任意**自定义规则语言（仅内置"国内直连"）。
- IPv6 分流（IPv6 目前根本没有接管，是独立缺口）。
- 多出口按规则分配。
- 引擎重新接管 DNS / fake-ip / gVisor 用户态协议栈（见第四节，均不采用）。
- 解决 Mac 上与 Clash TUN 同时开启的路由冲突。

**成功标准（验收）**

| # | 验收 | 方法 |
|---|---|---|
| 1 | 开关开启：国内 App 的流量在出口 `wf0` 上抓不到 | 出口 `tcpdump -ni wf0 host <设备 overlay 地址>` |
| 2 | 开关开启：访问 Google 仍经香港，能打开 | 抓包出现 Google 服务器 SYN-ACK；页面可打开 |
| 3 | 关闭开关：恢复现状（全部进隧道） | 抓包 |
| 4 | 长时间运行无掉线、无包风暴 | 引擎日志 `sendPacketBatch` 计数平稳；扩展 pid 不变 |
| 5 | 动态路由更新不打断已建立的连接 | 设备实测（见 M0） |

## 四、方案对比与决策

### 4.1 三个候选

| | 全部终结（Clash 式） | 两层 + gVisor 选择性终结 | **两层 + DNS 驱动动态排除路由（采用）** |
|---|---|---|---|
| 做法 | 所有连接在 gVisor 里还原后按规则转发 | 静态路由挡住大部分国内流量，剩下被规则点名的连接用 gVisor 终结后直连 | 静态路由挡住国内 IP；国内域名解析出的非国内 IP 动态加 `/32` 排除路由 |
| 扩展内存 | 高（iOS 上限约 50 MB，风险最高） | 中 | **几乎不增加** |
| 判断粒度 | 每条连接（可看 SNI） | 每条连接 | 每个 IP |
| 直连 socket 需绕过自己的隧道 | 需要（iOS 还没有 `bind interface`） | 需要 | **不需要**（直连由内核路由完成，引擎不发 socket） |
| 主要风险 | 内存、唤醒次数 | 内存、终结路径的复杂度 | 运行时更新路由是否打断连接；CDN 共用 IP 误判 |
| 改动量 | 最大 | 大 | 中 |

### 4.2 决策：采用第三列（分期落地，见 §八；M2 的具体路线见 §4.5）

理由：

1. **业界验证**：Tailscale 的 App Connectors（连接器充当指定域名的权威 DNS，解析成功后先为解析出的 IP 发布一条路由，再返回 DNS 应答）和 NetBird 的 DNS Routes（客户端定期解析域名，解析出的 IP 变成路由；默认开启 "Keep routes"，域名不再解析到某 IP 时旧路由保留以免打断长连接）都是这个模式。两者都在**路由层**处理域名，都没有用户态协议栈去终结每条连接。
2. **避开最大风险**：不新增协议栈，不碰 iOS 内存预算，也不需要给 iOS 补 `bind interface`。
3. **和手机上已跑通的路径兼容**：不改 DNS 方案 A，不让引擎回到"自己合成 DNS 应答"那条路（那条路在手机上出现过"应答发出、App 收不到"，根因至今未查明）。

### 4.3 与业界的一个关键不对称（必须正视）

Tailscale / NetBird 的域名路由是"**指定域名走 VPN**"，判断失误的后果是"多走了 VPN"，安全。
我们是"**指定域名直连**"：若某个 CDN 的 IP 既服务国内域名、又服务被封的国外网站，这个 IP 被加成直连排除后，那个国外网站就打不开。

缓解措施（写入设计，见 §5.4）：只对**确认属于国内域名表**的应答生效；动态排除路由**带过期时间**；总量有上限；国外域名永不产生排除路由。

### 4.4 明确不采用的做法

- **引擎重新接管 DNS（系统 DNS 指回 `10.96.0.1`）**：本期不做。手机上"引擎自己应答 DNS"的路径出现过应答未交付，根因未查明，见 `exit-node-routing-and-dns.md` §7。本设计改为**被动嗅探**隧道里回来的 DNS 应答，不代理、不合成任何 DNS 包。
- **fake-ip / IP→域名反查缓存**：不需要。嗅探应答时同一个包里同时有域名和 IP。
- **gVisor 终结**：不作为分流方案。它的收益只有「按连接判断（可看 SNI）」，而分流按 IP 判断已足够；代价是 iOS 扩展内存（约 50 MB 上限）、逐包用户态处理的耗电与延迟、直连 socket 需要 `bind interface`（iOS 版尚无）、UDP/QUIC/ICMP 需自行处理。gVisor 在本仓库的正确位置是「零授权嵌入」产品线（`shim.Server`），与出口分流是两回事。仅当 M1/M2 实测证明 CDN 共用 IP 的误判无法接受时，再评估「选择性终结」。

### 4.5 备选路线：DNS 分域名（M2 的候选 B，尚未验证）

**动机：** 风险 #3——国内域名被 `8.8.8.8`（经香港）解析，会得到境外 CDN 节点。若国内域名改由国内 DNS（如 `223.5.5.5`）解析，得到的多是国内 IP，直接落在第 0 层静态排除段里，就**不需要嗅探和动态路由**。

**结构性障碍（必须先正视）：**

- `NEPacketTunnelNetworkSettings.dnsSettings` 只有**一个** `NEDNSSettings`（一组服务器 + 一组 `matchDomains`），无法在原生设置里同时表达「国内后缀 → 国内 DNS，其余 → 隧道内 DNS」。
- 只给国内后缀设 `matchDomains` 会让其余域名回到运营商 DNS，即重现「google.com 被污染成假 Facebook 地址」（见 `exit-node-routing-and-dns.md` §3.2）。

**可行的实现路径（都待 M0 验证）：**

| 路径 | 做法 | 代价 |
|---|---|---|
| B1 原生 | 无法表达，仅列出以说明为何不可行 | — |
| B2 引擎分流 DNS | 系统 DNS 设为 `10.96.0.1`（`matchDomains=[""]`）；引擎收到查询后：国内后缀 → 转发到 `223.5.5.5`，其余 → `8.8.8.8`。`223.5.5.5/32` 加入排除路由，使引擎自己的上游 socket 由内核路由直连、不需要 `bind interface` | 引擎重新接管 DNS。§4.4 曾因「应答未交付」放弃这条路，需先确认该问题已由 `bd151981` 的交付修复解决 |

**结论：** B2 与 §4.4 的既有决定冲突，因此 **M2 不预设路线**：M0 验证 B2 的可行性（见 §八），M1 上线后测得的漏流量再决定走 A（嗅探 + 动态排除）还是 B2（引擎分流 DNS），或两者都不做。

## 五、设计

### 5.1 两层分流

```
                        ┌─ 第 0 层：静态排除路由（内核，零开销）
 App 的包 ──▶ 系统路由表 ─┤   国内 IP 段 ∈ excludedRoutes → 直接走物理网卡，不进扩展
                        │
                        ├─ 第 1 层：动态排除路由（内核）
                        │   国内域名解析出的、不在国内 IP 段里的地址 → 引擎动态加 /32 → 直接走物理网卡
                        │
                        └─ 其余 → utun → 隧道扩展 → WireGuard → 出口 NAT   （与现在完全一致）
```

引擎不转发任何"直连"流量，直连全部由**内核路由**完成，这是本设计不增加内存、也不需要 `bind interface` 的根本原因。

### 5.2 组件与边界

新增包 `apple/engine/split`，每个单元职责单一，可独立测试：

| 单元 | 职责 | 依赖 |
|---|---|---|
| `CNSet` | 国内 IPv4 段集合，`Contains(ip)`；`Routes()` 返回合并后的 CIDR 列表 | 内置数据文件 |
| `DomainMatcher` | 国内域名后缀匹配，`Match(name)` | 内置数据文件 |
| `DNSSniffer` | 从一个 IPv4/UDP 包解析出 DNS 应答，返回 `{name, ips[], ttl}` | 无（复用 `github.com/miekg/dns`） |
| `DynamicRoutes` | 维护动态排除集：`Add(ip, domain, ttl)`、过期、去重、上限、防抖批量输出变化 | 时钟（可注入） |
| `Policy` | 组合上面几个：对一次 DNS 应答产出"要新增的排除 IP" | 以上单元 |

集成点（只动三处，其余不变）：

1. **`packetTUN.Write`**：解密包写给系统之前，交给 `Policy` 只读地看一眼（不改包、不丢包）。
2. **`OnRoutesChanged`**：载荷从"包含的路由数组"扩展为对象 `{"included":[...],"excluded":[...]}`，Swift 侧同时兼容旧的数组格式，避免引擎与 App 版本不一致时出错。
3. **两个 `makeSettings`**：把 `excluded` 装进 `NEIPv4Settings.excludedRoutes`（与现有的控制面排除项合并）。

### 5.3 数据流（以国内域名为例）

```
① App 解析 douyin.com → 系统发 UDP 53 → 8.8.8.8（进隧道，和现在一样）
② 应答从隧道回来，经过 packetTUN.Write：
      DNSSniffer 解出 {douyin.com, [A, B], ttl}
      Policy：DomainMatcher 命中国内域名
              A 在 CNSet 内 → 已被第 0 层排除，什么都不做
              B 不在 CNSet 内 → DynamicRoutes.Add(B/32, "douyin.com", ttl)
③ 应答照常写给系统（原样，不延迟、不改动）
④ DynamicRoutes 防抖 ~2s 后合并输出变化 → OnRoutesChanged → Swift 重新应用 NE 设置
⑤ 之后新建的、发往 B 的连接直接走物理网卡
```

**已知竞态：** 步骤 ③ 与 ④ 之间，App 可能已经用 B 发出了第一个 SYN，它会走隧道（能用，只是走了出口）。之后的新连接直连。本期**接受**这个竞态，不延迟 DNS 应答（延迟会引入新的故障面）。

### 5.4 动态排除路由的收敛规则

| 规则 | 值（初始，可调） | 目的 |
|---|---|---|
| 仅国内域名表命中的应答才生效 | — | 国外域名永不产生排除路由（见 §4.3） |
| 过期时间 | `max(DNS TTL, 5 分钟)`，上限 1 小时；过期即撤销 | 避免陈旧 IP 长期误排除 |
| Keep 语义 | 域名再次解析到不同 IP 时，旧 IP 保留到自己过期 | 借鉴 NetBird 的 Keep routes，避免打断长连接 |
| 条目上限 | 512 条 `/32`，超过则淘汰最早过期的 | 控制 NE 路由数量 |
| 更新防抖 | 2 秒窗口批量合并，集合无变化不触发 | 避免频繁 `setTunnelNetworkSettings` |
| 不落盘 | 隧道重启后动态集合清空 | 避免陈旧状态 |
| 失败保底 | 任何解析/路由更新失败 → 该次不加排除，流量走隧道 | 失败方向永远是"多走隧道"，而不是断网 |

### 5.5 数据

| 数据 | 来源 | 存放 | 更新 |
|---|---|---|---|
| 国内 IPv4 段 | APNIC 公开的地址分配数据，合并成 CIDR | `apple/engine/split/data/cn_ipv4.txt`，`go:embed` | 脚本重新生成并提交；随 App 发版 |
| 国内域名表 | 社区维护的国内域名列表（如 v2fly `domain-list-community`）转成后缀集合 | `apple/engine/split/data/cn_domains.txt`，`go:embed` | 同上 |

- 生成脚本：`hack/scripts/gen-cn-lists.sh`（生成结果带版本戳与来源、日期头）。
- **待确认：** 域名表的开源许可证与体积（实现前确认；若体积过大，只取高频子集）。
- 数据只随 App 发布，不做在线更新（一期）。

### 5.6 开关与配置

- **位置：** `ExitNodeView`，仅当已选择出口节点时显示"国内直连"开关。
- **范围：** **每台设备各自设置**（本地），不经服务端、不改数据库。
- **传递：** App 写入 `providerConfiguration`（`splitRouting`）；运行时切换通过 `sendProviderMessage` 通知扩展，扩展调用引擎 `SetSplitRouting(enabled)`，引擎重新计算并回调 `OnRoutesChanged`。**切换不重连隧道。**
- 关闭时：静态与动态排除集合都清空，恢复现在的全局行为。

## 六、错误处理与安全

- **失败方向一致：** 所有异常路径的结果都是"该流量走隧道"（现状行为），永远不会因为分流逻辑出错而断网。
- **只读嗅探：** `DNSSniffer` 不修改、不延迟、不丢弃任何包；解析失败直接忽略。
- **隐私：** 域名只在内存里用于匹配，**默认不写入日志**；调试日志需显式开启。
- **资源上限：** 动态条目 512 条封顶；嗅探只处理源端口 53 的 UDP 包，其余包零开销通过。
- **DNS 走 TCP / DoH / DoT 的应用**：嗅探看不到，退化为只有第 0 层（IP 段）生效。已知限制，写入用户文档。
- **回退：** 关闭开关即回到现状；引擎里保留总开关，出问题可整体关闭分流逻辑。

| **M1** | **单独可交付**：第 0 层——`CNSet` + 生成脚本 + 引擎输出 `excluded` + Swift 装入 + 开关（`ExitNodeView` + `providerConfiguration`）。只做静态国内 IP 段，不做任何域名逻辑 | 验收 1–3；**并记录仍进入隧道的国内流量占比**（出口 `wf0` 上抓包统计），作为 M2 的决策依据 | 关开关 |
| **M2** | **由 M1 数据决定路线**，二选一或都不做：**A** 嗅探 + 动态排除路由（`DNSSniffer` + `DynamicRoutes` + `Policy` + 接入 `packetTUN.Write` + 防抖批量更新）；**B2** 引擎分流 DNS（§4.5） | A：国内域名解析出境外 IP 时被动态直连，验收 5；B2：国内域名由国内 DNS 解析，抓包确认 | 引擎总开关 |
| **M3** | 国内域名表 + 数据许可确认 + 用户文档（含已知限制）；仅在选了 M2 的 A 或 B2 时需要 | 域名规则命中率可用 | 同上 |
| **M4** | 长稳（≥24h）、内存与唤醒监控 | 无掉线、内存平稳 | 各层可独立关闭 |

每期独立提交；M1 起每步都在真机验证。**M1 完成时用户就能拿到「抖音直连」这个最主要的收益**；M2 及以后只在实测证明确有必要时才做。静态 IP 段这一层与平台无关，Android、Windows 可直接复用同一份 `CNSet` 数据。
